# ADR-011 · Resiliencia de la API REST y de la mensajería

Estado: implementado, 19/11/2026 (3.er checkpoint). Retoma lo pendiente del ADR-007 (durabilidad, outbox/inbox).

## Contexto

El checkpoint pide: timeout de 5 s con fallback, consumidores idempotentes y DLQ, que una caída del broker no pierda mensajes, Idempotency-Key y ETag en la API, y errores en Problem Details. El repositorio de pedidos sigue en memoria (JPA queda fuera de este corte).

## Decisiones

| Problema | Decisión | Dónde |
|---|---|---|
| Un reintento del cliente (doble clic, timeout de red) duplica la compra | `POST /pedidos` exige `Idempotency-Key`. Misma clave + mismo cuerpo → mismo pedido (`Idempotent-Replayed: true`). Misma clave + otro cuerpo → 422. En curso → 409 + `Retry-After`. Clave por usuario, vence a las 24 h, se libera si la operación falla | `IdempotenciaPedidos`, `PedidoResource` |
| Dos personas modifican el mismo pedido a la vez; tráfico repetido del catálogo | `ETag` fuerte (SHA-256 de la representación). `If-None-Match` → 304. `If-Match` desactualizado en cancelar/confirmar → 412 (concurrencia optimista) | `Etags`, `ProductoResource`, `PedidoResource` |
| Errores del framework (404 de ruta, 405, 415, EJBException) salían en HTML o texto | Mapper de red de seguridad `ExceptionMapper<Exception>` que recorre las causas y siempre responde `application/problem+json`, sin filtrar detalles internos | `Problemas`, `ErrorInesperadoMapper` |
| El broker está caído al crear el pedido | El pedido se guarda primero; si publicar falla queda en `ERROR_ENVIO` y la API igual responde 202. Un timer EJB cada 15 s lo republica (outbox simplificado) | `PedidoService`, `ReenvioDePedidos` |
| El broker (o el servidor) se cae con mensajes en la cola | Mensajes `PERSISTENT` en el journal de Artemis. Como el repositorio es en memoria, el MDB reconstruye el pedido desde el mensaje si no lo encuentra | `PublicadorPedidosJms`, `ProcesarPedidoMDB.rehidratar` |
| JMS entrega "al menos una vez" | Consumidor idempotente en dos niveles: registro LRU de `idMensaje` procesados y la máquina de estados (State) que absorbe duplicados | `RegistroDeMensajes`, `EstadosPedido` |
| Mensajes que nunca van a poder procesarse | `max-delivery-attempts=3` con backoff (1 s, 2 s, 4 s) y `dead-letter-address=ProcesarPedidoDLQ`. Un MDB los registra y un ADMIN los ve en `GET /api/admin/mensajeria/dlq` | `scripts/mensajeria.cli`, `MensajesMuertosMDB` |

## Verificación (19/11/2026, WildFly 41.0.1)

- `kill -9` del servidor con un pedido en la cola y el MDB frenado: al reiniciar, el pedido aparece PROCESADO (`entrega-3/evidencias/broker-caido-y-dlq.log`).
- Mensaje inválido: 3 intentos y DLQ (misma evidencia).
- Resto: `scripts/probar-resiliencia.sh` y `entrega-3/evidencias/probar-resiliencia.txt`.

## Consecuencias y límites

- La idempotencia y el registro de mensajes viven en memoria: sobreviven a reintentos, no a un reinicio. Con JPA pasan a una tabla (clave única).
- La rehidratación confía en el contenido del mensaje; es aceptable porque la cola es interna y sólo publica el propio WAR.
- La DLQ aparece en el log de arranque como "sin recurso" porque la crea el despliegue (anotación) después de que arranca el broker; una vez desplegado el WAR funciona (verificado).
